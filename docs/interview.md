## 2. CS 기술 Q&A

### ① Spring 코어
1. **DI/IoC** — 스프링이 객체를 만들어 주입 → 결합도↓·테스트 쉬움
2. **@Transactional 동작** — AOP 프록시가 시작/커밋/롤백을 대신 처리
3. **내부 호출이 안 먹는 이유** — self-invocation은 프록시를 우회
4. **REQUIRED vs REQUIRES_NEW** — 기존 트랜잭션 합류 vs 독립 분리. *실제 사례*: SMS 발송이 REQUIRED로 주문 트랜잭션에 합류해 알림 실패가 결제 전체를 롤백시킬 뻔한 결함을 감사에서 발견
5. **싱글톤 동시성** — 무상태면 안전, 가변 필드를 두면 위험

### ② Security & 인증
6. **JWT 위조 방지** — 서명(HMAC), 시크릿 없이는 위조 불가
7. **로그아웃 시 access 토큰** — 즉시 무효화 X. refresh는 Redis 화이트리스트에서 제거, access는 만료까지 유효(짧게 유지) + 회원 토큰은 폐기목록으로 즉시 차단
8. **인증 vs 인가 / 401 vs 403** — 누구냐 vs 권한 있냐 / 미인증 vs 권한 없음
9. **SecurityFilterChain** — stateless. 필터에서 JWT 검증 후 `AdminPrincipal`을 컨텍스트에
10. **refresh를 왜 Redis에** — 무효화·회전(rotation)·재사용 탐지

### ③ JPA / Hibernate
11. **영속성 컨텍스트** — 1차 캐시·더티체킹·쓰기 지연
12. **N+1 해결** — fetch join / batch size(IN 절로 묶기)
13. **LAZY vs EAGER** — LAZY 기본, EAGER는 불필요 조회·N+1 유발
14. **save vs saveAndFlush** — flush=DB 반영(커밋 전), commit=확정
15. **엔티티 생명주기** — 영속 상태일 때만 더티체킹 동작

### ④ MySQL / DB
16. **인덱스 원리·트레이드오프** — B-Tree 탐색 O(log n) / 쓰기마다 갱신 비용·공간
17. **격리수준** — 4단계, InnoDB 기본 REPEATABLE READ
18. **낙관 vs 비관 락** — `@Version`+재시도(경합 드묾) vs `SELECT FOR UPDATE`(잦음). 이 프로젝트는 재고 차감을 원자적 UPDATE + 조건절로 처리
19. **정규화 vs 반정규화** — 조회 성능을 위한 의도적 중복
20. **offset vs keyset 페이징** — §3 참고

### ⑤ Redis · 메시징
21. **캐싱 전략·3대 장애** — look-aside + stampede/penetration/avalanche 대응
22. **Redis가 빠른 이유** — 인메모리 + 단일 스레드(락 경합 없음) + IO 멀티플렉싱
23. **분산락** — `SET key val NX PX ttl`, 소유 토큰 검증 후 해제. 스케줄러 중복 실행 방지에 사용
24. **큐를 왜 쓰나** — 비동기·디커플링·부하 분산·장애 격리
25. **중복 전달 처리** — at-least-once 전제 → 멱등성(처리 키 중복 체크)
26. **DLQ** — 반복 실패 메시지를 격리해 큐 흐름 보호
27. **발행 실패 시** — best-effort 분리. 더 안전하게는 outbox 패턴(이 프로젝트에 `actionlog/outbox` 구현)
28. **SQS vs Kafka** — 관리형 큐(순서 보장 X, 소비 후 삭제) vs 로그(파티션 순서·재처리 가능). 전송 인터페이스로 교체 가능하게 둠

### ⑥ HTTP/REST & 테스트
29. **멱등성** — 여러 번 호출해도 결과 동일 / POST만 비멱등
30. **상태코드** — 200/201/400/401/403/404/409/429/500
31. **REST 원칙** — URL=자원, 메서드=행위, 무상태
32. **단위 vs 통합 / Mock** — 격리·속도 vs 실연동 / 가짜 부품으로 의존성 대체
33. **테스트 슬라이스** — 전체(`@SpringBootTest`) / 웹(`@WebMvcTest`) / 컨텍스트 없음(순수 단위)

## 3. 코드로 보여줄 수 있는 것 (라이브 데모 시나리오)

면접에서 화면을 공유할 수 있으면 아래 순서가 가장 짧게 많은 걸 보여준다.

1. **토큰 격리** — 회원 토큰으로 관리자 API 호출 → 401. `JwtTokenProvider`의 `type` 클레임과 필터, 그리고 이걸 검증하는 테스트.
2. **RBAC 스코핑** — CHURCH_MANAGER로 다른 교회 주문 조회 → 403. 요청에 다른 `churchId`를 넣어도 토큰 값이 이긴다.
3. **주문 상태머신** — 관리자에서 불가능한 전이 버튼이 안 보이고, API로 강제로 쏘면 400. 프론트 전이표는 백엔드와 **테스트로 동기화 검증**(`order-status.test.ts`).
4. **커서 페이징** — 감사 로그 "더 보기". `POST /v1/action-log/cursor`가 `(created_at, id)` 키셋으로 페이지를 잘라 오고 `COUNT(*)`가 없다. 왜 offset이 아닌지는 §2-20.
5. **비동기 감사로그** — 관리자 액션 → 큐 → 소비 후 적재. `EVENTLOG_TRANSPORT=kafka`로 바꿔도 코드가 그대로임을 보여준다.
6. **자기 감사** — AUDIT-REPORT.md의 결함 → 실제 수정 커밋 연결.

| **프론트 테스트가 얇음** | 관리자 16개(순수 로직·상태머신 동기화)뿐, 컴포넌트 렌더링·E2E 없음 |
| **캐시 무효화** | TTL 위주 + 일부 evict. 이벤트 기반 무효화는 미도입 |
| **사용자 웹 토큰이 localStorage** | XSS 노출 인지. 관리자 콘솔은 이미 NextAuth httpOnly 쿠키. 사용자 웹도 쿠키 세션이 정답 |
| **MSA는 실증 수준** | 감사·알림 2개만 추출, 실제 운영 토폴로지는 아님(`app.actionlog.source=remote`로 전환 가능) |
| **트래픽·장애 경험** | 실사용자 트래픽을 받아본 적 없음. 부하 테스트 수치는 없다고 정직하게 말할 것 |

## 5. 이 문서 유지 규칙

- 스택 버전·테스트 개수·한계 목록은 **코드에서 바로 확인 가능한 사실만** 적는다(추정 금지).
- 기능을 추가·삭제하면 §0 숫자와 §4 한계를 같은 커밋에서 갱신한다.
- 오래된 주장(예: "라이브 데모 없음")이 남아 있으면 그게 면접에서 가장 위험하다.
